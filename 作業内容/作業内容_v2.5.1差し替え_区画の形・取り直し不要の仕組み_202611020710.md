## したこと
1. **階の一覧の ▼ まとめ**（StationMapPanel.xaml.cs の FloorGroupKey・FloorGroupTitle）: 名前の数字を # にした鍵が同じ階をまとめる。見出しは「▼ Clinic Floor 01〜10（10 件）」（数字が 1 か所なら小さい方〜大きい方、2 か所以上なら最初と最後の名前を〜でつなぐ）。
2. **区画の形（案 A）**: 区画の形を、0.5 m の格子に塗って marching squares でなぞった輪郭（角が 45° に削れ、斜めの部品はギザギザ、0.5 m 膨らむ）から、床の板ごとの凸包そのものにした（StationFloorBuilder.Sections）。
   - 一覧に出す階の面積（30 m²）と階の名前の候補には、前と同じ格子の輪郭の面積（StationSection.PolygonArea）を使う → 一覧に出る階・名前は変わらない。
   - 区画の内外（SectionAt の OnRings・StationMapWeb.OnFloorShape）は凸包から 0.5 m（PaintMargin）以内も中とする（前の輪郭の帯と同じ幅）。
   - 区画の代表の点（SectionPoint）は輪の面積で重み付けした平均。
   - ビューア: 階段の形と同じく、枠（.sec-edge）を先に太く、塗り（.sec-fill、同じ色の 1 px の線つき）を上に描いて板の継ぎ目を隠す。選んだ区画・目的地の区画は上に移す。枠にも data-k。
   - JSON の形式を 17 に上げた（古い地図は「取り込み直しが要る」と出る）。
3. **取り直しをしなくてよい仕組み**（新しいファイル StationMeshCache.cs）:
   - starbreaker で書き出した GLB を読んだ直後の結果（socpak ごとの部品の名前・8 隅・形の数。表で選び分ける前）を、地図の JSON の横に `<名前>.meshes.gz` として保存する（地図の JSON を書けた後）。
   - 次の取り込みで、Data.p4k・木のハッシュ・保存の版（StationMeshCache.Version）・同梱の部品の表（station_mesh_kinds.json のハッシュ）が同じで、要る socpak が全部入っていれば、starbreaker を動かさず、表での選び分け（StationFloorBuilder.FromRaw）から先だけをやり直す。
   - 床・階・階段・道順の判定（段階 3・4）や、手元の部品の表を変えたときは、JSON の形式を上げれば、利用者の取り込み直しは数秒で終わる。GLB の読み方（ReadMeshes）・形の数（ShapeOf）を変えたときは Version を上げる（全部取り直し）。
   - 照合で Data.p4k の印だけ書き直すとき（RewriteStamp）は保存の印も書き直す。読めない保存は消す。地図を消すと保存も消す。容量の数え・使用量の表示・まとめての見積もり（1 インスタンス 45,000 バイト）に入れた。
4. **ハンガーからの道案内**（StationMapPanel.HangarLifts・HangarBanks）: 乗らない（elevator-noride）エレベーターのうち、同じ路線のエレベーターが全部同じ階にあり、その路線の行き先が地図に 1 つ以下のもの（路線のもう一方の止まる所＝ハンガーが地図の外）を「ハンガーのエレベーター」とし、並び（同じ階で 40 m 以内）ごとに 1 行、出発地・目的地の一覧に入れる。現在位置が区画の外のときの到着口にも入れる。シャトル乗り場の行の「シャトル乗り場: シャトル乗り場（→ …）」の二重を直した。
