## 利用者が決めたこと（このやり取りで決まった仕様の全部）
- ［詳細］で船・車両（NOITEM_Vehicle）を出しているとき、［3D 表示］（詳細の欄で出す。詳細の表に戻れる）と［別ウィンドウ］（モードレスの窓）を出す。
- 3D の操作（three.js 0.186.1 を同梱、ネットからは読まない）:
  - 左ドラッグで回転（船外は船のまわり／船内は見回す）、右ドラッグで平行移動、ホイールで拡大縮小（船内は前後移動）。
  - W/A/S/D で前後左右、↑/↓ で上下、Insert/Delete で拡大/縮小、Home で初期位置。
  - ［船外］［船内］の切り替え。船外の初期位置は左斜め前方の上から見下ろす（船全体が入る距離）。船内の初期位置は操縦席（目の高さぶん上げる）。船内は壁の当たり判定なし。
  - 右に縦のリスト: 操縦席・エレベーター・貨物室・タレット（データにあるものだけ、複数なら番号付きで全部）。押すとその位置へ（船内表示）。判定はノード名。
  - 船の前・上の向きは GLB を実際に調べて決める。
- 書き出し（取り込み）は常にテクスチャ付き・船内込み。書き出す前に予想時間と予想サイズを出す。取り消せる。
- 設定タブの「3D モデル」:
  - 置き場所（参照…付き）。既定は TEMP の中のアプリ用フォルダ。
  - 最大容量。初期値は置き場所のドライブの残り容量の 1/3（最大 2GB）。ドライブの全体と残りを出し、それ未満の値だけ指定できる。
  - 超えたら古いものから削除。
  - ［まとめて取り込む］: 保有船（my_ships と Hangar 同期の船を ResolveShipRecordNameReadOnly で record にしたもの）を優先し、その後に詳細の船一覧の残り。始める前に予想時間・合計の予想サイズ・隻数を出す。進み具合と残り時間を出し、取り消せる。最新のものは飛ばす。
- 予想は、--dump-hierarchy の参照ジオメトリを p4k list の大きさで合計（同名の末尾 m のファイルも足す）し、時間 ≈ 3 秒 + 0.05 秒/MB、サイズ ≈ 合計 × 1.35 とする（係数は定数、根拠をコメントに書く）。
- 進み具合（追加）:
  - 船ごとと全体の 2 本のバーで、％と予想残り時間を出す。
  - 個別の書き出しは裏で並行に動き、全体は動いている全部の合計（途中で足したらその分増える）。まとめて取り込むも同じ表示に載せる。
  - -v のログの段階で％と残り時間の精度を上げる。実績で係数を直す（並行で動いたものは使わない）。
- CPU とメモリ（追加）:
  - 書き出しを始める前に毎回 PC 全体の CPU 使用率を見て、90% 以上なら始めない（ダウンロード系のボタンを無効にし、待ち行列は止めて待つ）。止まっている理由を出す。
  - 同時数は min(論理プロセッサ数 ÷ 2, 空き物理メモリ ÷ 3GB)、最低 1。個別とまとめての両方に当て、上限なら待つ（「メモリ待ち」等を出す）。
- 別ウィンドウの船の切り替え（追加）: ［詳細］の検索に準じ、名前・メーカー・種類・サイズで絞る。
- ［読み込み］ボタン（追加）:
  - 取り込みは［読み込み］からだけ始まる。最新のキャッシュがあるとき・書き出し中は無効。
  - 表示のボタンでは書き出さず、［読み込み］を押すよう知らせる。読み込みが終わったら、その船を出している画面にそのまま表示する。
- パッチ後の照合と削除（追加）:
  - Data.p4k が変わったら、元データ（大きさと checksum）を照合し、同じならそのまま使う。
  - 違う（照合失敗も）ならその場で削除する。表示中・書き出し中は後で消す。
- マップの［現在位置］: 押したとき、今わかっている現在位置の星系が表示と違えば、取る前にその星系の表示に切り替える（MapPanel.xaml.cs の変更。この 3D の作業とは別に入ったもの）。
- ［詳細］の船・車両の【基本】に「積載量」の行を足す（【船・車両】の積載量はそのまま残す）。値は【船・車両】と同じ ShipCargo.Resolve（ゲームデータ → UEX → Ship Matrix）、0・不明なら出さない（GameDataQueryService.Detail.cs）。ビルドのみ確認、画面は未確認。
- 版は v2.4.0。

## 親が決めた細部
- キャッシュの名前は record の短い名前.glb。横に .json（Data.p4k のパス・大きさ・更新日時）を置く。
- 書き出しは一時ファイルに書いてから名前を変える。StarBreaker が選んだ record が違えば失敗にする。
- まとめて取り込むでは古いものを消して入れ替えない（保有船優先の意味が無くなるため）。予想サイズの合計が最大容量を超える手前で止める。
- GLB のライト（KHR_lights_punctual。600i で 1105 個）は使わない。環境光＋平行光、船内はカメラに付けた光。
- WebView2 は詳細の表とは別にし、SetVirtualHostNameToFolderMapping で同梱ファイルとキャッシュを別の仮想ホストにする。
- 同じ船は二重に書き出さず、動いているものに合流する。
- ％は「経過 ÷ (経過 + 残り)」で、終わるまでは 99% で止める。「予想にもとづく」とツールチップに書く。
- 進み具合はアプリ全体で 1 つの管理に集め、［詳細］と設定タブの両方で見られるようにする。
- アプリが扱うのは、横の .json にアプリの印（"App": "StarCitizenJapaneseTextCreater.ship3d"）があるものだけ。作業用フォルダは `_scjt_ship3d_work` とし、掃除は一時ファイルの名前の形に合うものだけ。相対パスの置き場所は保存しない。
- 照合の checksum は p4k の中央ディレクトリの CRC32。照合で同じと分かったら、.json の Data.p4k の印を書き換える。

## 実データで測った値（この PC）
- 書き出し（親の実測、テクスチャ付き・船内込み）:

  | 船 | 参照ジオメトリ合計 | 書き出し時間 | GLB |
  |---|---|---|---|
  | X1 | 35MB | 5 秒 | 26MB |
  | 600i | 135MB | 9 秒 | 147MB |
  | Polaris | 491MB | 26 秒 | 648MB |
  | Idris-P | 367MB | 26 秒 | 489MB |

- 参照合計の数え方（重複を除いたパスの p4k list の大きさ＋末尾 m のファイル、MB = 1,000,000 バイト）で、X1 35.4・600i 134.8・Polaris 489.4・Idris-P 366.3MB。上の値と合う。
- 実行時間:
  - `p4k list --filter "Data/Objects/**"` は約 4 秒・1,068,552 行。
  - `--dump-hierarchy` は約 2 秒。
- メモリ（親の実測）: 書き出し 1 本の最大は 600i 1.4GB、Polaris 2.9GB。
- 並行（親の実測、NVMe SSD 3 台、論理プロセッサ 24）: 600i を 1/2/4 本同時で、全体 9.3/9.3/10.9 秒、CPU 平均 10/19/30%。
- Data.p4k の中央ディレクトリ（LIVE、2026-10-29）:
  - エントリ 1,379,308 件、中央ディレクトリ 447MB。CRC32 が 0 のものは 63 件。
  - ZipArchive で読むと約 2 秒・作業メモリ約 970MB。
  - 自前の読み取りは大きさと CRC32 が ZipArchive と全件一致。ハッシュ表で 0.9 秒・作業メモリ最大約 96MB。
- テクスチャ:
  - GLB の materials の extras の .tif は、p4k では .dds。横に .dds.1〜.7・.1a〜.3a・.a の分割ファイルがある。
  - layers の path は .mtl。
- X1 の照合用の元ファイルは 525 個（dds 447・mtl 43、p4k に無い参照 1 個は大きさ -1 で記録）。
- `--dump-hierarchy` の出力:
  - 同じ船を 2 回出すと、オブジェクトのキーの並びが変わる。キーを並べ替えたハッシュは一致（X1 の 1 組で確認）。
  - 配列の終わりの前にカンマが残る（AllowTrailingCommas で読む）。
- メーカー: 船は items に行が無く、item_index.manufacturer を使う。ORIG は訳の DB のキーが manufacturer_NameOrigin なので引けず、「ORIG」と出る（［詳細］と同じ）。

## 検証で直した不具合
- 置き場所に既存のフォルダ（例 D:\）を選ぶと、起動時の掃除が `_work` を中身ごと消していた。容量の削除と使用量の集計も、アプリの書いていない .glb / .json を対象にしていた → アプリの印のあるものだけを扱う、作業用フォルダの名前をアプリ固有にする、掃除は一時ファイルの名前の形だけ、相対パスは保存しない。
- アプリを終えたとき、starbreaker が残ることがあった（取り消しの後始末が UI スレッドの継続だった）→ プロセスを登録し、終了時に同期的に Kill。
- EnforceLimit で、ファイルを消した後に f.Length を読んでいた（親が修正）。
- 照合で変わっていた船を「後で消す」側で、ボタンの状態の決め直し（RaiseStateChanged）が無かった（親が修正）。
- 執筆中に見つけて直したもの:
  - `--dump-hierarchy` の JSON の末尾のカンマで、見積もりの JSON の読み取りが失敗するはずだった。
  - csproj に `\t`（タブ文字）が入り、three.js がコピーされていなかった。
